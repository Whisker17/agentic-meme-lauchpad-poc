## Findings

### CR-01 — Invariant suites do not require successful trading coverage

**Severity:** Low — **non-blocking**

**Locations:**
- `contracts/test/invariant/LaunchpadHandler.sol:55–59`
- `contracts/test/invariant/LaunchpadHandler.sol:166–230`
- `contracts/test/invariant/MemeLaunchpad.invariant.t.sol:63–65`
- `contracts/test/invariant/MemeLaunchpad.invariant.t.sol:114–117`
- `contracts/foundry.toml:15–17`

**Description**

The handler tracks successful buys, sells, completions, and round trips, but the invariant suite never requires those counters to become positive.

When a quote and its corresponding trade both revert, the handler does not record a violation. Consequently, trading can be completely unavailable while the invariant suites remain green: reserve and supply assertions hold in the initial state, and fee and trade-violation counters remain zero.

Additionally, effective Foundry configuration has `fail_on_revert = false`. Unexpected handler reverts can therefore discard an action, including its accounting updates. Calls reaching a handler selector are not proof that the underlying trade succeeded.

**Reproduction**

In the temporary copy only, insert these guards at the start of the respective quote functions:

```solidity
// quoteBuy
if (amountIn > 0) revert ZeroOutput();

// quoteSell
if (amount > 0) revert ZeroOutput();
```

Run:

```bash
FOUNDRY_FUZZ_SEED=0x1 forge test \
  --match-contract 'MemeLaunchpad.*InvariantTest' -vvv
```

**Observed:** 12 passed, 0 failed, 0 skipped, despite every positive-amount trade being disabled.

This demonstrates a weakness in the invariant gate, not a claim that the original contracts cannot trade. Original-source tests and a separate successful-handler scenario passed. The ordinary unit/fuzz suite also provides independent protection against this mutation.

**Recommendation**

Add a deterministic handler coverage check requiring successful buys, sells, a genuinely executed round trip, and completion. Make unexpected handler reverts fatal after keeping expected protocol reverts explicitly handled.

For funded, valid trading actions, compare quote rejection against independently established expected behavior rather than treating agreement between two reverts as sufficient evidence.

### CR-02 — Oversized buy budgets overflow before final-buy truncation

**Severity:** Low — **non-blocking**

**Locations:**
- `contracts/src/MemeLaunchpad.sol:252–266`
- `contracts/src/MemeLaunchpad.sol:342–344`

**Description**

`quoteBuy` computes the fee on the full requested budget before determining whether the purchase should truncate. `_fee` evaluates `amount * FEE_BPS` using checked multiplication.

For sufficiently large budgets, this panics before the contract can reduce the actual payment to the completion cost. This is inconsistent with the otherwise useful “spend at most this amount” behavior: a caller need only possess the truncated payment, not the entire requested budget.

`buy` calls the same quote function, so both paths fail consistently. There is no quote/execution mismatch or persistent state damage.

**Reproduction**

With the DESIGN parameters and a fresh curve:

```text
quoteBuy(token, 1_000_000_000):
  amountInUsed = 606_060_607
  feeUsed      =   6_060_607
  netUsed      = 600_000_000
  completes    = true
```

Fund the buyer with exactly `606_060_607` quote base units and approve the launchpad for `uint256.max`.

Both calls below revert with `Panic(0x11)`:

```solidity
lp.quoteBuy(token, type(uint256).max);
lp.buy(token, type(uint256).max, 0, block.timestamp, buyer);
```

A control call with budget `1_000_000_000` succeeds using that same funding and delivers the full curve supply.

**Recommendation**

Determine the completion cost before evaluating arithmetic on an unbounded requested budget. If the budget meets that cost, return the truncated quote directly; otherwise evaluate the normal branch.

Alternatively, explicitly document and validate a supported budget bound. Merely replacing fee multiplication with full-precision arithmetic would not address every oversized-input addition in the existing normal-path expression.

## Curve, accounting, and lifecycle assessment

| Requirement | Assessment |
|---|---|
| **Curve arithmetic and rounding** | Normal buys and sells implement the normative ceiling-reserve equations. Fees round upward. The updated `priceE18 = vQ × 1e36 / vT` matches the specification and fits the reachable reserve bound for the DESIGN parameters. |
| **C1 — Solvency** | Buy liabilities increase by exactly the amount pulled: net reserve plus fee. Sell liabilities decrease by exactly the net quote paid: gross reserve reduction offset by the booked fee. Claims decrease balances and matching liabilities equally. Quote donations add surplus without changing reserves. No cross-curve drain was identified. |
| **C2 — No free round trip** | No profitable immediate buy/sell round trip was identified for the specified parameters. Split-sale fuzz tests and stateful checks passed. CR-01 limits how much confidence can be attributed to invariant success alone. |
| **C3 — Fee conservation** | Creator receives `floor(fee / 2)`; protocol receives the remainder. Claims clear the corresponding ledger before transferring. Fees of 1, 2, and 3 units are directly tested. |
| **C4 — Supply** | Supply is minted once to the launchpad; no later mint or burn entry exists. Without token donations, launchpad holdings equal unsold curve supply plus reserved supply. Donations increase holdings without increasing curve inventory or enabling withdrawals. |
| **C5 — Lifecycle** | Creation enters Trading; completion disables both trading directions and quotes. Graduated is unreachable. Completion stranding is an explicit accepted design decision, not a finding. |
| **C6 — Truncation** | Completing buys deliver exactly the remaining supply, pull only `amountInUsed`, and book fees from that amount. Quote and execution share the same implementation. CR-02 affects extreme requested budgets before this branch is reached. |
| **Dust / ZeroOutput** | Zero-net buys and zero-output buys/sells revert before transfers persist. Standard ERC20 transfer failures revert state and fee changes atomically. |
| **CREATE2** | Deployment and prediction use the same creator-bound salt and constructor arguments. Another creator cannot occupy the victim’s predicted address by copying its salt/name/symbol. Identical creator/salt/init-code reuse reverts; changing name or symbol changes init code and therefore the address. |

### Appendix B dispositions

- **R-1 — Truncation insolvency:** addressed. Reserve and fee updates use the actual truncated payment.
- **R-2 — Approval and simulation budget:** addressed in the inspected SDK builder: completing buys clamp both approval and BUY calldata to `amountInUsed`. Fork test source covers the clamp and race-time truncation.
- **R-4 — Dust and odd fees:** addressed through `ZeroOutput`, ceiling fees, creator floor-half, and protocol remainder.

### Session-key threat assessment

No path was identified that lets an untrusted session key bypass the hook’s recipient, quote-spend, or inventory restrictions through these contracts. In particular:

- `createToken` takes no payment and grants no caller inventory.
- Creator claims pay only the actual creator.
- A sell cannot name a victim as its source.
- Leftover quote allowance cannot be pulled independently of the account’s own buy.
- The reviewed token implementations have no callbacks that introduce an intervening trade or unrelated inflow during execution.

This does not provide execution-price protection or prevent an authorized session from spending its allowed budget poorly; those are explicit limits of the design.
